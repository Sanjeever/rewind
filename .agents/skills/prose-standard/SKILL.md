# 技术表达

- 先写读者需要知道的事实、规则或操作。能明确责任方时用主动语态，如「JS 管理播放队列」。一句集中讲一个主要观点，一段围绕一个主题。句长由信息决定。
- 使用界面上的实际操作名和实现中的标识。首次出现容易混淆的术语时说明含义，后续沿用同一称呼。
- 删除空泛开场、重复结论、装饰性修饰和代码已表达的执行细节。保留代码无法说明的兼容要求、设计原因和操作后果。有证据才写性能、稳定性和可用性判断。
- 改写前标出执行者、操作、条件、时序、责任归属、失败行为和证据范围。逐项对照改写前后，保留「必须」「应」「可以」等约束强度，避免把个别样本写成普遍保证。
- 博客、技术评论、思辨、叙事和原版发布寄语按其体裁编辑。保留作者的判断、措辞和节奏，核实可验证的事实。

例如「迁移完成后才标记成功」省略了判定条件。应用必须在旧值写入并读回校验成功后才能标记迁移完成。保留这个时序，维护者才能判断写入失败时如何处理。
